# 카드 5 — 계정 격리 검사와 인증 구현 설명서

## 할 일과 순서

1. 패스키로 등록한 서로 다른 계정 A/B와 서로 다른 가상 비공개 자료 3개씩을 준비한다.
2. A의 정상 조회와 B 자료 조회 시도를 나란히 기록한다. B에서도 반대로 검사한다.
3. 주소의 계정 ID를 바꾸면 403, 요청 본문의 계정 ID를 바꾸면 세션 소유자 자료만 200으로 반환하는지 확인한다.
4. 비로그인 열기, 정상 패스키 로그인, 이미 사용한 질문 재사용, 삭제된 패스키 로그인 각각의 성공·거절 요청과 응답을 기록한다.
5. 아래 인증 구현 설명서 6항목과 짧은 확인 방법, AI 역할을 작성한다. 검증 범위를 구분하고 미완료 항목을 남긴다.

## 이번 구현

- `server/authentication.mjs`의 비공개 조회는 GET/HEAD와 조회 전용 POST를 지원한다. POST는 자료를 쓰거나 수정하지 않는다.
- POST는 같은 Origin과 크기가 제한된 JSON 본문을 요구한다. 본문 전체를 파싱한 뒤 소유자 입력은 버리고 서버 세션의 user_id만 사용한다.
- GET/POST 주소의 userId/user_id/owner_id가 세션 소유자와 다르면 403이다. 중복 파라미터도 전부 검사한다.
- `scripts/verify-card5.mjs`는 실제 서버 핸들러에 Web Request를 보내고, 두 계정의 조회·양방향 거절·본문 변조·질문 재사용·잘못된 서명·삭제된 키·로그아웃 후 이전 쿠키를 검사한다.
- 이 스크립트의 DB와 암호 검증기는 테스트 대역이다. 프로덕션에는 테스트 API나 인증 우회 기능을 추가하지 않았다.
- `scripts/browser-owner-check.js`는 실제 브라우저의 현재 세션으로 조회 4개를 기록하는 보조 도구다. 쿠키를 읽거나 입력받지 않는다. 정적 배포에는 포함하지 않는다.
- `docs/card5-db-verification.sql`은 실제 DB의 별도 가상 계정·자료로 소유자별 조회와 RPC를 검사한 후 ROLLBACK한다. 실제 사용자 자료나 패스키는 바꾸지 않는다.

## ① 무엇으로 붙였나

기존 T01 HTML/CSS/JavaScript 소개 페이지를 복제한 T08에 Vercel 서버 함수와 `@simplewebauthn/server` 14.0.3을 연결했다.
DB는 Supabase 프로젝트 `gywwtgecjkfmgnwkbmzl`의 Postgres다. 직접 구현한 부분은 등록·로그인 API, 일회용 질문 저장/소비, 세션 쿠키, 소유자 확인, 패스키 관리와 비공개 UI다.
WebAuthn 옵션 생성과 서명 검증은 SimpleWebAuthn 라이브러리를 사용한다. Supabase Auth, OAuth, 이메일·비밀번호 로그인은 사용하지 않는다.

Vercel 환경변수 `SUPABASE_URL`, `SUPABASE_SECRET_KEY`는 서버에서만 사용한다. 개인키는 인증기/패스키 관리자에 남고 서버에는 credential ID, 공개키, 카운터, 이름, 저장 위치 메모를 저장한다.
Windows Hello PIN·휴대폰 잠금 해제 값은 사이트 비밀번호가 아니며 사이트에 입력하거나 보내지 않는다.

## ② 왜 그걸 골랐나

기존 정적 소개 페이지를 유지하면서 WebAuthn 서명 검증과 DB 접근만 서버로 옮길 수 있기 때문이다.
서명 검증은 라이브러리에 맡기고, 접근 권한은 서버 세션과 소유자 조건으로 매 요청 확인한다. 별도 웹사이트 비밀번호 없이 패스키로 잠금 영역을 연다.

## ③ 어디를 어떻게 고쳤나

| 흐름 | 브라우저 | 서버·DB |
| --- | --- | --- |
| 등록 | `passkeys.js`에서 `navigator.credentials.create()` | `api/passkeys.js` → `server/registration.mjs`: challenge 생성·저장 → 등록 검증 → t08_finish_registration 또는 t08_finish_additional_registration → 공개키 저장 |
| 로그인 | `private-access.js`에서 `navigator.credentials.get()` | `api/auth.js` → `server/authentication.mjs`: 새 challenge 저장 → 저장 공개키로 검증 → t08_finish_login에서 질문 사용 처리·세션 생성 |
| 로그아웃 | private-access.js에서 화면을 먼저 잠그고 POST logout | t08_sessions의 token_hash에 대응하는 세션 폐기 → 쿠키 만료. 같은 옛 쿠키도 이후 401 |
| 비공개 조회 | 로그인 후 `/api/private-info` 호출, textContent로 표시 | `api/private-info.js` → createPrivateInfoHandler → readSession → t08_private_items를 세션 user_id로 필터 |
| 패스키 삭제 | passkeys.js의 삭제 버튼 | t08_remove_passkey에서 소유자·남은 개수 검사 → 공개키 삭제·모든 해당 계정 세션 폐기 |

로그인 쿠키는 무작위 32바이트의 불투명 토큰이며 `__Host-t08_session`, Secure, HttpOnly, SameSite=Strict, Path=/, 1시간이다. DB에는 SHA-256 해시만 저장한다.
질문은 브라우저 바인딩 쿠키와 연결되고 5분 뒤 만료된다. 질문 소비와 세션 생성은 DB 트랜잭션으로 처리한다.
권한은 클라이언트의 loggedIn/userId 입력이나 등록 쿠키를 믿지 않고, 서버 DB의 만료되지 않고 폐기되지 않은 로그인 세션으로 판단한다.
T08 테이블 6개는 RLS를 켜고 anon/authenticated 직접 권한을 제거했다. 서버 전용 역할은 모든 행을 읽을 수 있으므로 서버 소유자 필터가 핵심 권한 경계다.

## ④ 안 열리는 것을 확인한 기록

### 실행한 자동 검사

- `npm test`: 32개 PASS / 0 FAIL.
- `npm run verify:card5`: 로컬 요청·응답 검사 11개 PASS. 결과는 `card5-local-evidence.json`.
- 실제 Supabase 검사: 가상 계정 A/B를 생성하고 서로 다른 본문 3개씩, 소유자별 조회, 질문 재사용 거절, 상대 키 삭제 거절, 삭제 키 제거와 세션 폐기, 로그아웃 세션 무효화를 확인하고 ROLLBACK했다.
- 실제 DB 권한: T08 테이블 6개 모두 RLS=true, anon/authenticated SELECT=false, service_role SELECT=true를 확인했다.
- 자동 검사와 DB RPC 직접 호출은 실제 WebAuthn 암호 검증·기기 조작·배포 HTTP 요청의 증거를 대체하지 않는다.

| 로컬 성공 요청 | 로컬 거절/변조 요청 | 기록 |
| --- | --- | --- |
| A GET /api/private-info → 200, A 자료 3개 | A GET ?userId=B → 403 FORBIDDEN | A-own / A-to-B |
| B GET /api/private-info → 200, B 자료 3개 | B GET ?userId=A → 403 FORBIDDEN | B-own / B-to-A |
| A/B 일반 조회 → 본인 자료 | POST 본문 userId=상대 → 200, 여전히 본인 자료 | A-body-tamper / B-body-tamper |
| 정상 로그인 → 200 authenticated=true | 같은 질문·응답 재사용 → 409 | loginSetup / used-challenge |
| 정상 패스키 로그인 → 200 | 잘못된 서명 판정 → 401 | loginSetup / invalid-signature |
| 정상 세션 조회 → 200 | 로그아웃 후 똑같은 쿠키 → 401 | B-own / old-cookie-after-logout |
| 등록된 키 로그인 → 200 | 삭제된 credential 로그인 → 401 | loginSetup / deleted-key |
| 로그인 후 비공개 조회 → 200 | 쿠키 없는 직접 조회 → 401 | A-own / anonymous-denied |

JSON의 Cookie는 전부 `[REDACTED]`다. 개인키·PIN·DB 비밀키는 보고서에 넣지 않는다.
실제 브라우저 Network/HAR에는 쿠키·서명·개인 자료가 포함될 수 있으므로 원본을 그대로 제출하지 않고 필요한 요청·응답만 마스킹해 기록한다.

### 실제 두 계정 검사를 남기는 순서

1. 기존 계정 A를 삭제하지 않는다. 별도 브라우저 프로필/시크릿 창에서 로그인하지 않은 상태로 새 패스키를 등록해 B를 만든다. A로 로그인한 채 추가 등록하면 A의 백업 키이므로 B가 아니다.
2. Supabase SQL Editor에서 `select id, created_at from public.t08_users order by created_at;`로 테스트 계정을 구분한다. 비공개 본문이 비어 있으면 서로 다른 내용의 격리를 시각적으로 입증할 수 없으므로, 별도 테스트 계정 두 개와 가상 자료를 사용한다. 실제 사용자 계정 본문은 이번 작업에서 수정하지 않았다.
3. 각 계정으로 실제 로그인한 창에서 scripts/browser-owner-check.js를 Console에 붙여 넣고 `await t08CheckOwner('상대 테스트 계정 UUID')`를 실행한다. 결과를 A/B 각각 기록한다. UUID가 실제 상대 계정인지 확인해야 한다. 자기 UUID를 넣으면 상대 거절 검사에 실패해야 정상이다.
4. 실제 자료가 들어 있는 상태에서 보고서를 공유하지 않는다. 공개 제출용 내용은 만들어 넣은 가상 자료만 사용한다.
5. 로그인/재사용/삭제 흐름은 Network에서 성공과 거절을 나란히 기록한다. 재사용은 성공한 verify 요청과 같은 질문 ID·credential 응답·그때의 바인딩 쿠키를 서버에 다시 보내는 검사다. 성공 후 바인딩 쿠키가 지워지므로 단순 버튼 재클릭만으로는 같은 요청의 재사용 검사가 되지 않는다. 쿠키 원문은 제출하지 않는다.

## ⑥ 아직 못 막은 것 / 미완료

- 휴대폰 인증 뒤 “문제가 발생했습니다. 다른 기기에서 프로세스를 다시 시작하여 다시 시도하세요.” 안내가 남지만 PC에서는 로그인과 비공개 조회가 성공한다는 사용자 보고가 있다. 원인은 아직 확정하지 못했다.
- 실제 패스키를 가진 두 별도 테스트 계정과 서로 다른 가상 본문으로 수행한 배포 요청·응답 증거는 아직 없다. 로컬·롤백 DB 검사를 이 증거로 표시하지 않는다.
- 실제 배포에서 잘못된 서명, 같은 사용 완료 질문의 재전송, 로그아웃 후 동일한 이전 쿠키를 재전송한 원문 마스킹 기록은 별도로 수집해야 한다.
- 질문 유효시간은 5분이다. 시간이 너무 길지 않은지 운영 상황에 맞춰 더 검토할 필요가 있다.
- 마지막 패스키 삭제는 차단한다. 외부에서 모든 키를 잃거나 DB 등록이 제거되면 기존 계정 복구 수단이 없다.
- 공개 첫 등록에는 별도 초대 제한이나 요청 빈도 제한이 없다. 다른 사람의 계정 생성과 등록 요청 남용까지 막는 운영 정책은 미구현이다.
- npm 접근 제한으로 의존성 lockfile은 아직 생성하지 못했다. 버전은 14.0.3으로 고정했다.
- C12의 “실제 개인정보 없음”을 제출물 전체에 엄격하게 적용하면 기존 T01의 실제 공개 연락처·학력과 충돌한다. 공개정보를 유지하라는 사용자 결정에 따라 임의 변경하지 않았다. 현재 가상 자료 선언은 검사용 비공개 본문에만 적용하며 C12 전체 충족이라고 주장하지 않는다.
