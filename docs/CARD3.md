# T08 카드 3 — 패스키 로그인과 비공개 조회

## 구현

- 기존 카드 2에서 등록한 패스키와 공개키를 그대로 사용한다. 재등록할 필요가 없다.
- POST /api/auth?action=options: 새로운 로그인 질문을 생성하고 DB에 5분간 보관한다.
- POST /api/auth?action=verify: DB 질문, Origin, RP ID, 사용자 확인, 저장된 공개키의 서명을 SimpleWebAuthn으로 검증한다.
- 질문은 별도의 HttpOnly 브라우저 바인딩 쿠키에 묶는다. 다른 브라우저에서 가져온 질문은 사용할 수 없다.
- 질문은 서버에서 한 번만 소비한다. 검증 후 DB 함수가 질문 행과 패스키 행을 잠그고 질문 사용 완료, counter 갱신, 세션 생성을 한 트랜잭션으로 처리한다.
- 패스키의 사용자 ID는 서버 DB에서 찾는다. 클라이언트가 보낸 사용자 ID를 로그인 소유자로 채택하지 않는다.
- discoverable credential을 사용하므로 로그인 시 기기에서 기존 패스키를 선택한다. 이메일·비밀번호 입력란은 없다.

## 서버 세션

- 서버가 32바이트 임의 토큰을 생성하고 __Host-t08_session 쿠키로 전달한다.
- 쿠키 속성은 HttpOnly, Secure, SameSite=Strict, Path=/이며 유효기간은 1시간이다.
- DB에는 원본 토큰 대신 SHA-256 해시, 소유자 ID, 만료 시각, 폐기 시각만 저장한다.
- 카드 2의 등록 직후 확인 쿠키는 비공개 정보 접근 권한을 부여하지 않는다.
- GET /api/auth?action=session은 서버 세션의 유효 여부만 반환한다.
- GET /api/private-info는 매번 서버 세션의 만료·폐기를 검사한 뒤 그 사용자 ID에 속한 자료만 반환한다.
- 로그인 전, 만료 후, 로그아웃 후에는 401이다. 다른 소유자 ID를 쿼리에 지정하면 403이다.
- 응답에는 private, no-store를 설정한다. 토큰·개인키·PIN·서버 키는 JSON 응답이나 로그에 적지 않는다.

## 비공개 항목

서버 DB t08_private_items에 사용자별로 아래 제목 3개를 저장한다.

- 준비 중인 프로젝트 메모
- 개인 목표와 진행 상황
- 스스로 쓰는 회고

본문은 요청대로 비워 두었다. 로그인 후에는 제목과 '아직 작성한 내용이 없습니다.'를 표시한다.
제목·본문은 비로그인 HTML이나 공개 JavaScript에 넣지 않는다. 가져온 문자열은 textContent로 렌더링한다.
이 단계에는 비공개 본문 편집 기능이 없다. 패스키 추가·삭제는 CARD4.md를 참고한다.

## 로그아웃

- POST /api/auth?action=logout은 DB 세션을 폐기한 뒤 쿠키를 지운다.
- 화면에서는 요청을 시작하는 즉시 비공개 내용을 제거한다. 서버 폐기에 실패하면 성공으로 안내하지 않고 재시도를 요구한다.
- 기존 토큰을 복사해 갖고 있어도 DB 폐기 상태를 검사하므로 다시 접근할 수 없다.
- 새 로그인 시 현재 브라우저의 이전 세션도 폐기한다.
- 뒤로 가기 캐시, 늦게 도착한 조회 응답이 로그아웃 후 내용을 다시 표시하지 않도록 처리했다.
- 같은 Origin의 다른 탭에는 토큰 없이 로그인·로그아웃 상태 변경만 전달한다.

## DB 변경

선택한 ALEPH_Task 프로젝트에 다음 구조를 추가했다. 기존 사용자·패스키와 다른 과제 자료는 삭제하지 않았다.

- t08_auth_challenges: 로그인 질문과 브라우저 바인딩 해시
- t08_sessions: 로그인 세션 해시·만료·폐기
- t08_private_items: 소유자별 비공개 항목
- t08_finish_login: 검증 후 질문 소비·counter 갱신·세션 발급

모든 새 테이블에 RLS를 활성화하고 PUBLIC/anon/authenticated 접근을 제거했다. service_role만 접근한다.
DB 함수는 SECURITY INVOKER이며 anon/authenticated 실행 권한이 없다.
RLS 정책 없음 INFO는 일반 역할의 접근을 전부 막는 서버 전용 설계에 따른 것이다.
SQL은 이미 적용했으므로 docs/card3-schema.sql을 같은 DB에 다시 실행하지 않는다.
새로운 Vercel 환경변수는 필요하지 않는다.

## 자동 검사와 한계

- 기존 검사 포함 Node 테스트 24개 통과.
- 로그인 질문 고유성·저장, 서명 검증 성공/실패 이후의 처리, 질문 재사용·만료·브라우저 바인딩·userHandle 불일치, 세션 만료·교체, 로그아웃 후 같은 쿠키 재사용, 다른 소유자 접근, 등록 쿠키 격리를 검사했다.
- UI에서 textContent 렌더링, 로그아웃 즉시 삭제, 늦은 응답 차단, pagehide 시 비공개 DOM 제거도 검사했다.
- 자동 테스트의 WebAuthn 암호 검증기는 모킹했다. 실제 PIN 인증을 통과한 증거로 사용하지 않는다.
- 실제 DB에서는 테스트 입력으로 로그인 저장 트랜잭션·counter·질문 재사용 차단·항목 3개 생성·세션 폐기를 검사하고 ROLLBACK했다. 테스트 계정과 세션은 남기지 않았다.
- 실제 기기의 PIN·등록된 패스키로 로그인하는 검사와 성공·거절 요청의 최종 증거는 배포 후 남겨야 한다.

## 배포 후 순서

1. 정식 사이트에서 패스키로 로그인을 누르고 기존에 등록한 패스키로 PIN 등 기기 확인을 완료한다.
2. /api/auth?action=verify와 /api/private-info가 200인지, 본인 항목 3개가 나타나는지 확인한다.
3. 새로고침 후 로그인 상태와 본인 항목이 유지되는지 확인한다.
4. 로그아웃한 뒤 비공개 내용이 사라지고 /api/private-info가 401인지 확인한다.
5. 다시 로그인할 때 이전과 challenge 값이 다른지 비교한다.
6. 별도 검사에서 잘못된 서명, 이미 사용한 질문, 로그아웃 전 쿠키의 재요청이 거절되는지 기록한다.

실제 세션·쿠키·토큰은 제출 기록에서 [MASKED]로 가린다. Network의 원본 쿠키를 채팅이나 공개 저장소에 붙이지 않는다.
로그인 완료만으로 C30·C31·C33의 거절 증거까지 확보되었다고 판정하지 않는다.
